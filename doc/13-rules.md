# 13. Жёсткие правила работы

**Проект:** Muhomor.spb.ru (AmanitaLove.ru) · **Версия CMS:** 2.5 · **Актуально на:** 24 октября 2026

---

## 1. Обзор

Этот файл фиксирует **обязательные правила** работы над проектом. Нарушение этих правил **недопустимо** — они выработаны опытом и защищают проект от потери данных, поломок и лишних затрат.

Правила действуют для **всех участников**: владельца, внешнего разработчика (Deepseek), тестировщика.

---

## 2. Правило 1 — Не удалять комментарии в коде

**Формулировка:**

> **НЕ УДАЛЯТЬ КОММЕНТАРИИ В КОДЕ.** Если файл обновляется — все старые комментарии должны остаться. Новые правки комментируются.

**Что это значит:**

- При обновлении файла **нельзя** удалять существующие комментарии (`//`, `/* */`, `#`, `<!-- -->`).
- Новые правки **обязательно** комментируются (что изменено, зачем).
- Комментарии — это **история решений**. Их потеря = потеря контекста.

**Пример:**

```php
// БЫЛО:
// $count = readCounter(); // старый вызов, без блокировки

// СТАЛО (19.10.2026):
// $count = readCounterWithLock(); // flock() — защита от race condition
```

**Почему:**

- Комментарии объясняют **почему** код такой, а не только **что** он делает.
- При возврате к файлу через месяцы — комментарии спасают.
- Новый разработчик (или AI) видит историю, не ломает старое.

## 3. Правило 2 — Формат передачи Markdown в чате

**Формулировка:**

> **ФОРМАТ ПЕРЕДАЧИ MARKDOWN В ЧАТЕ:** файлы и большие фрагменты Markdown передаются в **блоке markdown** (тройные обратные кавычки с указанием языка `markdown`). Внутри блока — обычный Markdown: заголовки, переносы строк, пустые строки между абзацами, `**жирный**`, инлайн-код, таблицы, списки, ссылки.
>
> **Тег pre не использовать** — при отправке через чат он теряет переносы строк, текст склеивается в одну строку.

**Что это значит:**

- Если нужно передать **файл в формате Markdown** (README, документация, инструкция) — весь текст оборачивается в **один блок**.
- Внутри блока — **обычный Markdown** (с переносами строк, жирным, обратными кавычками, заголовками, списками, таблицами).
- Пользователь копирует текст **без** внешних тройных обратных кавычек — получает чистый Markdown-файл.

**Решение проблемы вложенных блоков (обязательно к применению):**

Если внутри передаваемого Markdown-файла **есть пример блока кода** (тройные обратные кавычки), внешний блок нужно оборачивать **четырьмя** обратными кавычками, а не тремя. Тогда вложенные три кавычки не разорвут внешний блок.

**Правило:** если в тексте файла встречаются тройные обратные кавычки — внешний блок всегда из **четырёх** обратных кавычек.

**Почему:**

- pre **не сохраняет переносы** при отправке через чат — текст склеивается в одну строку (проверено на практике).
- Блок markdown **корректно рендерит** переносы, таблицы, списки (проверено на 15 файлах документации).
- Внешний блок из **четырёх** кавычек **не ломается** при вложенных блоках кода.
- Не требует ручного удаления pre/pre.
- Стандарт для GitHub, Deepseek, ChatGPT.

## 4. Правило 3 — Экономия токенов при правке файлов

**Формулировка:**

> **ЭКОНОМИЯ ТОКЕНОВ — ПРАВКА ФАЙЛОВ:**
> - При правке **ОДНОЙ строки** — присылать только **фрагмент** + указание, куда вставить. Полный файл не присылать.
> - При объёме правки **БОЛЬШЕ ОДНОЙ строки** — **ПРЕДЛОЖИТЬ варианты:** (а) фрагмент, либо (б) весь файл целиком. Выбор за пользователем.

**Что это значит:**

- Если меняется **одна строка** (например, `sitemap.php` — переименовать `fileMTime` → `getFileMtime`) — присылается **только фрагмент** (строка до / строка после) + указание, куда вставить.
- Если меняется **больше одной строки** (например, переписать `counter.php` целиком) — **сначала спросить**: «прислать фрагмент или весь файл?»
- **Не присылать** полный файл, если изменения коснулись одной строки.

**Пример (одна строка):**

```php
// Файл: sitemap.php
// Найти строку:
$lastmod = fileMTime($file);

// Заменить на:
$lastmod = getFileMtime($file);
```

**Пример (больше одной строки):**

> «Правка затронет 15 строк в counter.php. Прислать фрагмент (с указанием, куда вставить) или весь файл целиком?»

**Почему:**

- Экономия токенов (полный файл = много токенов).
- Меньше шума в чате.
- Пользователь сам решает, что удобнее.

## 5. Правило 4 — Экономия токенов при общении

**Формулировка:**

> **ЭКОНОМИЯ ТОКЕНОВ — ОБЩЕНИЕ:**
> - Общаться **ПОШАГОВО**: вопрос — ответ. Не вываливать сразу много разной информации.
> - **НЕ размещать без спроса никакой код.**
> - Если требуется внести изменения в файлы — **СНАЧАЛА СПРОСИТЬ:** «прислать вам фрагмент кода или весь файл?»

**Что это значит:**

- **Пошагово:** один вопрос — один ответ. Не «вот всё сразу: архитектура, код, тесты, roadmap».
- **Без спроса — никакого кода.** Сначала спросить: «Нужен код? Фрагмент или файл целиком?»
- **Сначала спросить** — потом делать. Не «вот вам готовое решение», а «вот план, подтвердите».

**Пример:**

> Плохо: «Вот полный admin.php с фильтром заказов, вот admin.js, вот CSS, вот тесты...»

> Хорошо: «Фильтр заказов затрагивает admin.php и admin.js. Прислать фрагмент или файлы целиком?»

**Почему:**

- Экономия токенов.
- Пользователь не тонет в информации.
- Меньше вероятность, что правка «не туда».

## 6. Правило 5 — Критическое мышление

**Формулировка:**

> **КРИТИЧЕСКОЕ МЫШЛЕНИЕ:** если предложенное решение кажется плохим или ломает архитектуру — сказать об этом прямо.

**Что это значит:**

- Если пользователь предлагает решение, которое **ломает архитектуру** (например, «давайте заменим JSON на SQLite») — **сказать прямо**: «Это плохая идея, потому что...».
- Если решение **противоречит** уже принятым правилам (например, «удалим комментарии для чистоты») — **напомнить правило**.
- Если **риски** (например, «инлайн `tailwind-output.css`») — **предупредить** (уже ломали вёрстку на Windows-хостинге).

**Пример:**

> Пользователь: «Давайте заменим JSON на MySQL — так надёжнее.»

> Ответ: «Плохая идея. Архитектура flat-file — сознательный выбор: простота, переносимость, бэкап. MySQL усложнит развёртывание и добавит точку отказа. Если нужна атомарность — уже есть flock(). Предлагаю оставить JSON.»

**Почему:**

- Внешний разработчик (AI) **не должен** слепо выполнять всё.
- Критика **спасает** от ошибок.
- Опыт предыдущих сессий показывает: некоторые «улучшения» ломают проект.

## 8. Чек-лист соблюдения правил

**Перед отправкой сообщения:**

- [ ] Я не удалил комментарии в коде?
- [ ] Если это MD-файл — он в блоке markdown (не в pre)?
- [ ] Если внутри MD-файла есть блоки кода — внешний блок из **четырёх** обратных кавычек?
- [ ] Если правка одной строки — я прислал фрагмент, а не весь файл?
- [ ] Если правка больше одной строки — я спросил «фрагмент или файл»?
- [ ] Я не вывалил сразу много информации?
- [ ] Я не разместил код без спроса?
- [ ] Если решение плохое — я сказал об этом прямо?

**Перед правкой файла:**

- [ ] Я спросил «фрагмент или файл»?
- [ ] Я сохранил все старые комментарии?
- [ ] Я прокомментировал новые правки?
